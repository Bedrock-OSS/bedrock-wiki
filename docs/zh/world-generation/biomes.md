_最后更新于 1.16.210_

:::warning
自 1.18 起，自定义生物群系在 Minecraft Bedrock 中已损坏
:::

:::warning
生物群系自定义是*实验性的*。使用包含生物群系定义的行为包的每个世界必须启用实验性游戏玩法开关。当前声明正确的情况下，现有的功能可以很好地工作；但声明不正确的组件和属性可能会导致崩溃，而不仅仅是记录错误。此外，由于[继承模型](#inheritance)存在的问题，自定义生物群系所使用的模式目前构建得并不完善。
:::

:::warning
[下界生物群系生成](#the-nether)在版本 1.16.210 中存在错误。下界生物群系现在通过 `"multinoise_generation_rules"` 组件进行自定义。然而，自定义生物群系目前无法使用此组件生成。同时，在原版覆盖中使用旧的 `"nether_generation_rules"` 组件将导致该生物群系在下界中无法生成。
:::

行为包允许自定义生物群系。行为包可以创建全新的**自定义生物群系**，或对先前声明的生物群系进行[**覆盖**](#inheritance)，例如原版生物群系。生物群系连接到关键的游戏机制中，例如生物生成、数据驱动游戏玩法和自定义方块的展示。生物群系还启用了一个强大的系统，用于添加花朵和树木等装饰物，或甚至像塔楼和房屋之类的结构；这些装饰物和结构统称为[特征](#/concepts/features/)，它们对世界生成至关重要，但（通常）在范围和构建上与生物群系分离。

虽然覆盖和自定义生物群系提供的功能大致相同，但自定义生物群系是创建全新游戏体验的推荐方式。覆盖应保留原始生物群系的身份和意图，仅应保留用于：

-   轻微的表面、高度图或气候调整
-   世界生成中生物群系稀有度的重新分配
-   添加新特征或生物，但仅在主题合适的情况下

当需要*任何*独特的游戏体验，或对先前声明的生物群系的调整会从根本上改变其性质时，应使用自定义生物群系。自定义生物群系大放异彩的情况示例包括：

-   需要新的或极端的地形来实现某种美学。
-   需要某个地方来生成自定义特征，例如新的树木类型。
-   需要替代或更具挑战性的游戏体验，可能使用新的生物和结构。

> 由于生物群系模式中的遗漏，这些建议有一些例外。例如，在尝试强制原版主世界生物群系在额外位置生成时，似乎只需要原版覆盖，但这可能是不可能的，因为[生物群系如何注册自己以进行生成](#regions)。这意味着生物群系的美学可能必须通过多个生物群系定义文件迭代克隆，每个文件都根据需要调整其生成规则。

## 生物群系定义

生物群系在行为包顶层 `biomes` 目录中以 `*biome_name*.json` 或 `*biome_name*.biome.json` 形式的文件中声明。`biomes` 目录中不能使用子目录来分组生物群系定义；`biomes` 子目录中的所有定义都将被忽略。

[因为标识符必须与文件名匹配](#description)，与其他声明生物群系的行为包可能会发生命名空间冲突。一种避免冲突的策略是使用反向域名方案。_biome_name_ 可以包含句点来按嵌套顺序对生物群系进行分组，例如 `biomes/fancycraft.fantasy_realms.magical_springs.hills.mutated.json`。在这里，`fancycraft` 是开发者，`fantasy_realms` 是行为包，`magical_springs` 是[顶层生物群系](#heirarchy)名称，`hills` 和 `mutated` 是[子生物群系](#subbiome-types)类型，`json` 是必需的文件扩展名。（此示例中省略了可选的 `.biome` 扩展名。）

> 在顶层 `biomes` 目录中声明的无效 JSON 文件更可能记录错误，但也可能导致崩溃。直接放置在此目录中的非 JSON 文件会被忽略。如果 `biomes` 中直接存在的文件以 `.` 开头，游戏当前总是会崩溃。这可能会导致问题，例如用于项目配置的文件，甚至 macOS 上臭名昭著的 [.DS_Store 文件](https://en.wikipedia.org/wiki/.DS_Store)。

### 格式

与行为包中的所有构建资源一样，生物群系定义以 JSON 编写，例如：

<CodeHeader></CodeHeader>

```json
{
    "format_version": "1.13.0",

    "minecraft:biome": {
        "description": {
            "identifier": "pumpkin_pastures"
        },

        "components": {
            "minecraft:surface_parameters": {
                "foundation_material": "minecraft:stone",

                "top_material": "minecraft:grass",
                "mid_material": "minecraft:dirt",

                "sea_floor_depth": 4,
                "sea_material": "minecraft:water",
                "sea_floor_material": "minecraft:sand"
            },
            "minecraft:overworld_height": {
                "noise_params": [0.125, 0.0625]
            },

            "minecraft:climate": {
                "temperature": 0.375,
                "downfall": 0.25,
                "snow_accumulation": [0, 0.5]
            },

            "minecraft:overworld_generation_rules": {
                "generate_for_climates": [["cold", 1]],

                "hills_transformation": "pumpkin_pastures_hills",
                "shore_transformation": "pumpkin_pastures"
            },

            "overworld": {},
            "pumpkin_pastures": {},

            "animal": {},
            "monster": {}
        }
    }
}
```

> 无效的 JSON（与附加组件的所有方面一样）会导致生物群系定义失败；该生物群系将不会在世界 中生成。不幸的是，不会抛出错误。JSON 验证器和/或语法高亮器可以轻松解决这个问题。

#### 格式版本

<CodeHeader></CodeHeader>

```json
"format_version": "1.13.0"
```

顶层属性 `"format_version"` 描述了后续模式所符合的版本规范。生物群系的最新发布的 `"format_version"` 是 `"1.13.0"`。

> 1.12 的先前版本存在但已被弃用，在较新版本中无法使用。在该版本中，生物群系标识符充当顶层对象属性的键，该属性本身直接包含格式版本、组件和标签。本文档仅使用 `"1.13.0"` 格式，但可能在其他地方看到已弃用的版本。

版本必须采用 _\_release_._major_._minor\__ 的形式，其中 _minor_ 或 _major_ 和 _minor_ 都是可选的。所有 3 个标识符必须是整数，但完整的版本号不必代表真实的 Minecraft 版本。当前，任何大于或等于 `1.13.0` 的版本号都可以使用，并将引用 `1.13.0` 规范，但建议仅使用 `1.13.0` 或开发期间的目标版本：未来版本可能会影响整体模式。

#### 生物群系规范

<CodeHeader></CodeHeader>

```json
"minecraft:biome": {
	…
}
```

另一个顶层属性是 `"minecraft:biome"`，它建立了生物群系定义的模式。

##### 描述

<CodeHeader></CodeHeader>

```json
"description": {
	"identifier": "pumpkin_pastures"
}
```

`"minecraft:biome"` 属性的 `"description"` 属性用作生物群系的元数据。它目前只包含一个属性 `"identifier"`，用于唯一标识一个生物群系。这里的值必须与文件名匹配，不含 `.json` 或 `.biome.json` 扩展名。例如，如果标识符是 `prairie`，文件名必须是 `prairie.json` 或 `prairie.biome.json`。此标识符用于从多个生物群系定义属性中引用。

> 与附加组件的其他方面不同，生物群系在其标识符中不接受被文件名忽略的命名空间前缀（例如 `elysium:`）。可以提供这样的前缀，但文件必须包含该前缀，包括冒号；这样的文件名在许多支持 Minecraft 的文件系统中无效，因此不应使用这种传统命名空间系统。考虑使用[反向域名系统](#biome-definitions)代替。

##### 组件

<CodeHeader></CodeHeader>

```json
"components": {
	…
}
```

`"minecraft:biome"` 属性还包含 `"components"` 属性，这是生物群系定义的核心。这里声明的组件放置、塑造和设计生物群系。

> 组件详情分散在本文档的其余部分；由于其交互的复杂性，它们无法像这些包装属性那样被整洁地描述或组织。

组件始终是对象属性，即使是那些应该充当布尔值的属性。例如，`"minecraft:ignore_automatic_features"` 组件属性不是分配 `true` 或 `false`，而是分配一个空对象 `{}`：

```json
"components": {
	…

	"minecraft:ignore_automatic_features": {}
}
```

尽管 JSON 可能无效，但可以 在 `"components"` 对象中使用同名的属性来表示组件。虽然应该避免这种情况，但应该注意，游戏只会使用提供的组件的最后一个实例：更早定义的组件中的值将被完全忽略。例如：

```json
"components": {
	…

	"minecraft:overworld_height": {
		"noise_type": "ocean"
	},
	"minecraft:overworld_height": {
		"noise_params": [1.25, 0]
	}
}
```

尽管 `"noise_type"` 属性通常会[完全覆盖](#heightmap) `"noise_params"` 属性，但在此示例中，由于组件在 `"components"` 对象中的顺序，预设将被忽略。

当在生物群系定义中使用组件时，*必须*提供其所有必需属性；如果没有，将抛出错误并且生物群系将无法生成。

> 由于继承模型的工作方式，如果生物群系定义中跨继承链的不完整组件包含该组件模式所需的属性，该组件将正确工作。有趣的是，当两个组件都位于同一个生物群系定义文件中时，情况并非如此。如前所述，即使缺少必需属性，也只会使用后一个组件。

###### 标签

<CodeHeader></CodeHeader>

```json
"components": {
	…

	"overworld": {},
	"pumpkin_pastures": {},

	"animal": {},
	"monster": {}
}
```

除了用于创建生物群系的组件外，`"components"` 属性还允许添加任意标签。标签看起来像空组件，例如 `"animal": {}`。标签名称必须符合正则表达式 `[a-z0-9_.:]+`，即：小写拉丁字母、阿拉伯数字、下划线、句点和冒号。

> 为了提高兼容性，不建议创建带有 `minecraft:` 前缀的标签，以确保标签不会与未来 Mojang 定义的组件冲突。此外，建议在这些标签中使用特定于行为包的命名空间，以最大程度地减少与其他行为包的冲突，例如 `"betterbiomes:arboreal"`。

### 继承

生物群系定义文件可以根据行为包排序充当初始定义或覆盖。行为包堆栈中生物群系定义的首次出现标志着自定义生物群系的创建；同一生物群系在行为包堆栈中的后续定义可以通过继承修改或覆盖先前定义。

只有 `"components"` 属性中的组件和标签会被继承。单个组件内的属性也通常会被继承。不幸的是，某些组件或组件属性对象需要完全重新声明所有它们的属性才能工作，这意味着在覆盖时通常最好重新声明整个组件。继承总是会发生，除非新组件会干扰先前存在的组件，这通常是[表面构建器](#inheritance-considerations)的情况。

没有办法表示应该从先前定义中移除属性。这在[标签](#tagging)方面尤其麻烦，因为标签用于表示生物群系的放置位置以及它们如何为其他游戏机制提供动力（如生物生成）。如果由于继承问题产生冲突，建议将生物群系的所需元素提取到新的自定义生物群系中，并尝试从[世界生成](#generation)中移除旧生物群系。

如果覆盖先前声明的生物群系，生物群系文件可能无用般地为空。如果生物群系定义（初始或覆盖）包含任何组件，它必须包含顶层 `"format_version"` 属性，一直到 `"identifier"` 属性。生物群系的初始定义必须至少包含一个组件或标签；所需的声明很小，因为几乎每个生物群系方面的默认值都可用作后备。

## 生成

生物群系选择在世界中进行放置的规则取决于三件事：

1. 生物群系为其注册的维度
2. 生物群系在特定槽位中生成的潜力，相对于在同一槽位注册的任何其他生物群系*在加载区块时应用于世界的所有行为包*
3. 该槽位使用的来自世界种子的不可变随机噪声表面

> **槽位**可能代表整个维度或其表面区域的子集。槽位的概念在实际文档或模式中不存在。此术语用于表示可以从中选择生物群系的专用区域，或者为单一目的独立连接的生物群系集合。

_生物群系布局不是每个世界随机化的，而是每个种子随机化的。_ 这意味着如果将包含相同自定义生物群系定义的相同附加组件应用于具有相同种子的两个新世界，每个维度在两个世界中将包含完全相同的生物群系布局。这对原版生成来说是显而易见的，因为相同的种子将始终在相同位置生成相同的原版生物群系。

Minecraft 目前没有办法创建新的维度。末地不允许添加新生物群系或移除默认生物群系，只留下主世界和下界可以自定义。

> `"minecraft:legacy_world_generation_rules"` 组件在 Mojang 提供的文档中注明会影响传统有限世界，但没有为此组件提供模式，也没有原版生物群系定义使用它，其目的和行为未知。

### 主世界

<CodeHeader></CodeHeader>

```json
"minecraft:overworld_generation_rules": {
	"generate_for_climates": [
		["cold", 1]
	],

	"hills_transformation": "pumpkin_pastures_hills",
	"shore_transformation": "pumpkin_pastures"
}
```

主世界使用[**气候**](#climates)、[**区域**](#regions)和[**层级**](#hierarchy)的概念来确定如何放置生物群系。

生物群系主要使用 `"minecraft:overworld_generation_rules"` 组件与主世界生成交互。在这里，它们可以注册自己为基本生物群系并声明它们的子生物群系。不幸的是，[标签系统](#tagging)也会影响[区域](#regions)的槽位。

气候和区域形成重叠在主世界上的独立、不可配置的槽位地图。具有指定气候槽位和区域槽位的生物群系只能在该种子的槽位地图的相关交叉处生成。换句话说，生物群系只能生成在匹配气候和区域类型的主世界区域中，气候和区域绑定限制生物群系可能生成的表面积。生物群系可以直接作为基本生物群系放置在这些交叉处，而子生物群系可以在这些基本生物群系中声明，以便进行更精细的地形细节处理。

生物群系使用[权重](#climates)在槽位交叉的可用区域上竞争。实际上，生物群系实例不是根据种子预先确定的；相反，相关槽位的可用空间按权重划分。因此，生物群系添加到槽位交叉处将导致生物群系*变小*而不是*更稀有*；反之亦然。因为气候和温度地图的大小不可配置，调整生物群系权重是修改生物群系大小的唯一方法。

#### 气候

<CodeHeader></CodeHeader>

```json
"generate_for_climates": [
	["frozen", 2],
	["cold", 1]
]
```

生物群系必须与温度类别对齐才能作为基本生物群系生成。要将生物群系提升为将在主世界生成的基本生物群系，该生物群系的定义必须在 `"minecraft:overworld_generation_rules"` 组件内包含 `"generate_for_climates"` 数组属性。此数组包含形式为 [*climate type*, *weight*] 的数组值，其中 _climate type_ 是五种气候字符串之一，_weight_ 是一个整数值，反映生物群系生成的机会。生物群系在每个声明的气候类别内按权重生成，在生物群系声明的[区域](#regions)内生成，并在其范围内生成[子生物群系](#hierarchy)。

> 这里的气候温度不同于 `"minecraft:climate"` 组件中的浮点属性 `"temperature"`，后者用于设计而非放置。然而，传统上，它们在游戏目的上是相关的。

> 如果为 _weight_ 提供了浮点值，该值将被截断，向下舍入到最接近的较小整数。如果 _weight_ 设置为负值，其行为将如同设置为 `0`。

5 种气候按温度升序排列：

| 气候 | 属性值       |
| :--- | :----------- |
| 冻结 | `"frozen"`   |
| 寒冷 | `"cold"`     |
| 中等 | `"medium"`   |
| 温带 | `"lukewarm"` |
| 温暖 | `"warm"`     |

> 温带气候仅适用于[海洋](#basic-oceans)和[深海](#deep-oceans)。陆地仅使用其他 4 种气候类型。

生物群系权重作为槽位交叉的共享分母的分子。例如：

一个虚构的生物群系 X 权重为 5。放置在此目标槽位的所有生物群系（包括生物群系 X）的组合权重为 20。因此，生物群系 X 有 5/20，即 25% 的生成机会。

可以通过**去权重**：将其 `"generate_for_climates"` 属性的权重在所有适用气候中设置为 `0` 来通常移除原版生物群系。然而，Minecraft 实际上有一个[激进的回退系统](#regions)来防止去权重导致的生成失败，因此这种策略可能不足以移除生物群系。[取消槽位](#regions) 或添加自定义生物群系可能是从生成中移除生物群系的必要方法。

> 如果一个气候的所有生物群系都设置为不生成，Minecraft 将使用其他气候的生物群系来填补该气候指定的空间。回退系统甚至可以生成完全去权重或[取消槽位](#regions)到未使用的气候槽位的生物群系，通常优先考虑气候槽位而不是[区域槽位](#regions)。因此，建议始终至少为[常见陆地](#common-land)和[海洋](#oceans)的每个气候生成一个生物群系。由于其大小，[稀有陆地](#rare-land) 可以忽略：原版生成在冻结气候中根本没有稀有陆地。

Minecraft 仅允许玩家首次加载在少数生物群系中：

-   平原
-   森林
-   针叶林
-   暗森林
-   热带草原
-   丛林

这些生物群系的变体，例如破碎热带草原和花森林，也允许玩家加载。如果由于去权重（并且在平原和森林生物群系的情况下，另外未被列为[深海子生物群系](#islands)），这些生物群系都不存在，玩家通常将无法加载到世界：游戏最常会无限期地搜索有效的生成位置。

> 在一些罕见的、难以解释的情况下，在经过足够时间尝试找到有效的加载位置后，玩家将被抛入世界原点处不允许玩家加载的生物群系。

与[区域槽位](#regions)不同，生物群系可以注册到多个气候。例如，如果一个生物群系在不同的气候中传播是合适的，可以使用它。平原生物群系就是一个例子，它分布在 3 种气候中：

<CodeHeader>biomes/plains.json</CodeHeader>

```json
"generate_for_climates": [
	["cold", 1],
	["medium", 3],
	["warm", 1]
]
```

如果同一生物群系在两个相邻气候中生成，并且这些独立的生物群系实例彼此相邻，该生物群系看起来会合并为一个，没有气候区域边界的指示。

#### 区域

主世界由许多区域组成，这些区域充当生物群系放置的槽位。显然按陆地和海洋划分，专用槽位以复杂的方式相关联。

> 生物群系的性质（其美学和游戏玩法）不必符合它们所放置区域的意图。这里使用的"陆地"和"海洋"区域名称因此有些误导：放置在[陆地区域](#land)中的生物群系可以是水生的，而放置在[海洋](#oceans)中的可以代表陆地。这些只是在这里这样命名，以参照原版生成。

[如上所述](#climates)，生物群系使用 `"minecraft:overworld_generation_rules"` 组件中的 `"generate_for_climates"` 属性直接放置在主世界中，但这里给出的值仅影响气候槽位地图。配置生物群系在特定区域生成是不直观的，甚至未被 Mojang 文档化。主世界依赖于存在[特定标签](#overworld-generation-aspects)将生物群系槽位在区域地图上。

在某些情况下，生物群系可以在主世界中从其区域**取消槽位**，迫使它们作为更高优先级的槽位生成。此更改对于后续列出的行为包是不可逆的，因为它依赖于[生物群系定义继承模型](#inheritance)。Minecraft 使用激进的回退系统试图在槽位交叉处没有注册生物群系时防止生成失败。由于回退系统的激进性，在某些情况下，取消槽位是移除不需要生物群系的唯一方法；[去权重](#climates)可能不够。

##### 陆地

与现实世界不同，陆地构成了主世界的大部分。陆地技术上由于与海洋的混合和限制而包含几个奇怪的子槽位。如上所述，生物群系实际上不必代表陆地：这只是槽位的名称；它们可以是水生的或包含海洋子生物群系。

总共有 56 个原版陆地生物群系，其中许多是基本生物群系的变种或山地形式。

###### 常见陆地

<CodeHeader></CodeHeader>

```json
"generate_for_climates": [
	["cold", 1]
]
```

常见陆地是游戏中最大的槽位，构成了绝大部分陆地。Minecraft 中的大多数生物群系都放置在这里，例如沙漠、暗森林、平原和沼泽。_默认情况下，所有自定义生物群系都放置在常见陆地中，除非另有标记。_

```
	当通过将其气候权重设置为 `0` 来指示所有常见陆地生物群系不生成时，Minecraft 使用[稀有陆地](#rare-land)槽位的生物群系来填充此槽位，从侵蚀恶地和巨型树木开始。如果这些生物群系也被取消槽位并设置为不生成，游戏会按回退生物群系列表 descend：

- 丛林变体
- 剩余的巨型树木变体
- 蘑菇田
- 桦木森林变体
- 剩余的恶地变体
- 沙漠变体
- 自定义生物群系及其变体
- 森林变体
- 海洋变体

然后，回退生物群系将在主世界的整个陆地上生成。为此列表选择的变体通常可能作为子生物群系在未修改的生成中出现。海洋生物群系是陆地的最终回退，因为标签继承：没有办法将海洋生物群系取消槽位到海洋槽位，因为它们在其原版定义中已经具有 `"ocean"` 标签。稀有生物群系将继续放置在稀有陆地槽位中，直到它们被取消槽位到海洋。
```

###### 稀有陆地

<CodeHeader></CodeHeader>

```json
"minecraft:overworld_generation_rules": {
	"generate_for_climates": [
		["medium", 1]
	]

	…
},

"rare": {}
```

稀有陆地槽位是主世界中相当大但非常不常见的区域，专门留用于生物群系。当为生物群系应用 `"rare"` 标签时，它们会被放置在这里。原版生成中的稀有生物群系示例包括中等气候中的丛林、温暖气候中的恶地和寒冷气候中的巨型树木。原版生成中没有冻结气候的稀有陆地，但可以通过自定义添加：

<CodeHeader></CodeHeader>

```json
"minecraft:overworld_generation_rules": {
	"generate_for_climates": [
		["frozen", 1]
	]
},

"rare": {}
```

> 稀有陆地生物群系可以通过应用 `"ocean"` 标签来取消槽位。这是因为 `"ocean"` 标签优先于 `"rare"` 标签。如果由于取消槽位，在给定气候中特定稀有陆地的实例没有可用的 `"rare"` 标签生物群系，游戏将回退到兼容的常见陆地生物群系。这种情况自然发生在冻结和温带气候中，那里没有原版稀有生物群系。但是，如果稀有陆地生物群系仅为特定气候[去权重](#climates)，如果该气候没有其他生物群系可用，该生物群系仍然可以生成。

##### 海洋

主世界的其余部分被海洋覆盖。海洋是一个用词不当的名称，因为它们在世界中并不完全连接；相反，主世界的陆地区域表现得像这样，以给玩家更多空间，导致海洋更像是海洋或湖泊。生物群系使用 `"ocean"` 标签放置在海洋区域。

海洋主要由普通深度和深海深度划分，权重大致相等。岛屿可以分散在海洋区域内生成。默认情况下，总共有 10 个海洋生物群系：五种温度和两种深度的每种组合各一个。海洋生物群系不一定必须生成为水生生物群系；它们可以是陆地。此外，海洋可以包含陆地子生物群系。例如，平原、森林和海滩不仅海洋独有，但可以作为海洋岛屿的一部分生成，这些岛屿本身位于海洋区域内。

> 海洋权重的行为与其他分布不同。表面上，海洋并非为了竞争空间而设计：原版生物群系对每种深度-气候组合只有一个海洋生物群系。权重相似的竞争海洋在非常小的尺度上分离：每个实例约几个方块。权重的更大差异确实更清晰地分离了竞争生物群系，但权重较小的生物群系仍然只会生成在非常小的丛中。一般来说，使用[表面调整](#surface-adjustments)或[特征](#features)来转换海洋更为明智。

> 如果通过[去权重](#climates)将所有海洋设置为不生成，游戏会回退到冰冻海洋和深海冰冻海洋。由于此回退，添加自定义生物群系可能是移除所有原版海洋生物群系的唯一方法。

###### 基础海洋

<CodeHeader></CodeHeader>

```json
"minecraft:overworld_generation_rules": {
	"generate_for_climates": [
		["lukewarm", 1]
	]
},

"ocean": {}
```

基础海洋约占海洋区域的一半。该区域旨在用于深度相对较浅的水生生物群系。

> [尽管深海槽位如何发生](#deep-oceans)，原版基础海洋生物群系不能使用 `deep` 标签取消槽位。它将继续生成，除非被[去权重](#climates)。

###### 深海

<CodeHeader></CodeHeader>

```json
"minecraft:overworld_generation_rules": {
	"generate_for_climates": [
		["frozen", 1]
	]
},

"ocean": {},
"deep": {}
```

使用 `deep` 标签以及 `ocean` 标签放置在深海区域。深海构成了海洋中剩余的大部分空间。这个槽位通常用于比其他海洋延伸更深的海洋，通常从表面到基岩的一半左右。

> 单独的 `"deep"` 标签对生成或生成没有影响；它必须与 `"ocean"` 一起使用。

###### 岛屿

<CodeHeader>biomes/ocean.json</CodeHeader>

```json
"minecraft:overworld_generation_rules": {
	"hills_transformation": "tropical_island"
},
```

从概念上讲，岛屿与陆地区域中的子生物群系没有什么不同。 vanilla 中生成的岛屿实际上只是海洋中的"山丘"！

> 虽然这些岛屿从技术上讲不形成槽位，而是子生物群系，但由于这是一个 bug 还是一个疏忽，它们因必须如何声明而被记为槽位。岛屿永远不会为自定义海洋生物群系声明，只能按海洋深度单独分组。岛屿仅使用 `minecraft:overworld_generation_rules` 组件中的 `hills_transformation` 或 `mutate_transformation` 属性在 `ocean` 和 `deep_ocean` 生物群系的覆盖定义中声明（即使这些原版海洋已被[去权重](#climates)）。如果需要稀有度，岛屿也可以声明为[变种山丘](#mutated-hills)。 vanilla 中的岛屿仅使用山丘子生物群系生成，并且仅在深海中生成；因此，通过在深海的覆盖中将 `hills_transformation` 指向深海生物群系本身，可以完全禁用 vanilla 岛屿：

<CodeHeader>biomes/deep_ocean.json</CodeHeader>

<CodeHeader></CodeHeader>

```json
"minecraft:overworld_generation_rules": {
	"hills_transformation": "deep_ocean"
},
```

由于[生成陆地时如何优先处理海岸](#shores)，海洋中的岛屿可能完全形成海岸，除非这些海岸被禁用。岛屿也可以有自己的河流子生物群系； vanilla 岛屿和所有自定义生物群系默认使用河流。

##### 蘑菇田

非常罕见地，蘑菇田作为自己的槽位在海洋区域内生成。蘑菇田生物群系本身可以通过添加 `"ocean"` 标签取消槽位来禁用。然而，蘑菇田海岸生物群系无法通过[任何方式](#exceptions)禁用，当主生物群系被取消槽位时，它将完全覆盖该槽位；这是主世界中唯一放置位置不可变的生物群系。尝试将蘑菇田海岸生物群系取消槽位到海洋似乎最初可以工作，但生物群系将同时继续在蘑菇田槽位中生成。

> 如果不需要蘑菇田，更改它们的样式是最方便的方案——使它们与周围海洋融为一体——是唯一的办法。

#### 层级

<CodeHeader></CodeHeader>

```json
"minecraft:overworld_generation_rules": {
	…

	"hills_transformation": [
		["overgrown_forest_hills_short", 4],
		["overgrown_forest_hills_tall", 1]
	],
	"shore_transformation": "rocky_shore"
}
```

主世界生物群系可以直接或间接由世界生成器放置。在这里直接放置的生物群系称为**基本生物群系**，而通过基本生物群系间接放置的生物群系将称为**子生物群系**。

如果在 `"generate_for_climates"` 属性中声明了目标气候温度，生物群系将表现为基本生物群系。直接放置的生物群系通常很大。

基本生物群系的所有子生物群系都将存在于基本生物群系的范围内，并位于其关联的槽位交叉处。因此，这些子生物群系是间接放置的，不是在主世界中声明自己的生成，而是依赖于基本生物群系的生成。

> 生物群系可以无限制地被引用：它们可能同时作为基本生物群系出现，并作为多个其他生物群系的子生物群系。

子生物群系*从不*继承其引用生物群系的任何方面。如果子生物群系应该以与其引用生物群系相似的方式出现或表现，它必须重新声明相关组件才能这样做。

##### 权重

<CodeHeader></CodeHeader>

```json
"mutate_transformation": [
	["crater", 2],
	["lava_pit", 1]
]
```

可以为每种转换类型声明多个子生物群系。在基本生物群系中声明时，可以为它们分配整数值权重以改变其出现次数。例如，山丘子生物群系实际上只是基本生物群系的一个小而常见的子区域，因此它可用于形成许多不同的场景。例如，一个基本生物群系可以同时有山丘和湖泊"山丘"子生物群系。

> 当浮点值用于权重时会发生截断。因此，权重 `0.5` 将表现为权重 `0` 并且不会生成。

基本生物群系可以从其加权子生物群系声明中引用自身。[与基本生物群系权重一样](#overworld)，这具有减少实际子生物群系可用空间的效果，使它们的表面积更小，而不是按数量使它们更稀有。对于使用山丘子生物群系的丘陵基本生物群系，这可用于制作小型、稀有的山峰。对于使用河流子生物群系的干燥、温暖的基本群系，河流可以偶尔出现干涸，而不依赖于山丘或变种子生物群系。

##### 覆盖

当覆盖先前的生物群系定义时，为特定子生物群系类型设置的值——无论是直接生物群系引用还是加权引用数组——将完全替换该类型的任何先前定义。这意味着如果较早的定义和新覆盖都为一种类型提供了多个子生物群系，旧的子生物群系将完全被新的覆盖，而不是添加。

例如，如果较早的定义声明了：

<CodeHeader></CodeHeader>

```json
"hills_transformation": [
	["rolling_hills", 2],
	["spiky_hills", 1]
]
```

而新定义声明了：

<CodeHeader></CodeHeader>

```json
"hills_transformation": [
	["tall_hills", 1],
	["short_hills", 1]
]
```

只有 `"tall_hills"` 和 `"short_hills"` 子生物群系将作为山丘转换生成。之前的列表*完全*被忽略。如果要一起使用两组，必须在新定义中重新声明之前的子生物群系：

<CodeHeader></CodeHeader>

```json
"hills_transformation": [
	["rolling_hills", 2],
	["spiky_hills", 1],
	["tall_hills", 1],
	["short_hills", 1]
]
```

##### 子生物群系类型

基本生物群系可以声明以下类别的自己的子生物群系：

| 转换 | 属性值                    |
| :--- | :------------------------ |
| 山丘 | `"hills_transformation"`  |
| 变种 | `"mutate_transformation"` |
| 河流 | `"river_transformation"`  |
| 海岸 | `"shore_transformation"`  |

[山丘](#hills)和[变种](#mutations)是固定的、分散的、有边界的区域，它们可以有自己的子生物群系，包括[变种山丘](#mutated-hills)。[河流](#rivers)形成细长的、不可改变的 stretches，分布在世界各地。[海岸](#shores)的放置同时受其他生物群系的影响；它们形成陆地和海洋之间的分界线。

嵌套子生物群系没有效果。山丘不能有进一步的山丘。所有子生物群系类型都是如此。山丘、变种和变种山丘都可以声明自己的河流和海岸子生物群系，从而在子生物群系规模上进行精细的调整。河流和海岸不会生成任何子生物群系。

###### 山丘

<CodeHeader></CodeHeader>

```json
"hills_transformation": "pumpkin_pastures_hills"
```

山丘子生物群系是生物群系的小而常见的子区域，通常用于高程变化。尽管名称如此，它们不必用于生成丘陵地形。它们在基本生物群系中生成的机会足够常见，可以可靠地用于形成大型、自然的生成，如湖泊、火山口等。山丘子生物群系用于在原版深海中生成岛屿。山丘没有默认值；不声明山丘子生物群系时生成不会发生任何变化。

###### 变种

<CodeHeader></CodeHeader>
