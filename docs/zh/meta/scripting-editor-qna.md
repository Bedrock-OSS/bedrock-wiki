## QuickJS

-   **问**：是否有计划添加 jit 编译以让脚本运行更流畅？
-   **答**：挑战在于，即使对于支持 JIT 的 JS 引擎（如 V8），也不是所有我们的目标设备都支持。
-   **答**：在其他地方和本帖中提到过，但我们的 JavaScript 引擎不支持 JIT。如果我们有一天转向不同的 JS 引擎，我们可以研究 JIT（在某些平台上，至少如此，不幸的是我们的许多平台不支持 JIT）。
-   **问**：是否有计划很快远离 QuickJS？
-   **答**：我们目前没有计划很快远离 QuickJS。
-   **答**：我们确实希望脚本覆盖尽可能多的场景，是的，获得正确的性能基线是实现这一目标的重要部分，也是我们希望继续改进的。有两个方面：确保我们创建的 API 范式对常见用例具有高性能，以及改进基础 QJS 集成（以及 Bedrock 引擎本身）。

我们与 Java modding 框架（特别是 fabric）形成鲜明对比，因为归根结底我们是引擎之上的版本化合约，而不是修改引擎的方式。但我们也希望它易于使用和强大！

## 用 JS 读写 json

-   **问**：你们是否计划允许用 JavaScript 读写 JSON？
-   **答**：是的，如果您将 JSON 文件放入脚本文件夹，您可以将其作为导入读取，尽管有关于从脚本文件夹外部读取 JSON 的问题吗？不太可能支持从行为包中的其他地方加载/解析 .json 文件。
-   **答**：如果您有自己的数据文件供自己使用，并且想使用 .json 作为创作的格式，您应该能够通过将其放入脚本来做到这一点。但它是只读数据。
    您不能将任意文件（.json 或其他）保存到任何地方。
-   **答**：我可能会与一些人聊聊天，因为我可能只是在引擎中做原型，我会回复你这个问题 😅。但我完全理解脚本本身中的这个目标场景，我也听到了关于脚本文件夹之外的反馈，但这更复杂。

## 脚本替换的不仅仅是 JSON 事件

-   **问**：脚本会替换的不仅仅是 JSON 事件吗？如果是这样，我们是否能够通过使用脚本来创建行为，还是它只会坚持替换 JSON 事件？我可以看到一个需要，我们可以创建高级实体组件甚至物品和方块组件，也许甚至可以控制它们在其他脚本事件触发或返回 true 时的行为方式。
-   **答**：是的，脚本不仅仅是 JSON 事件，但脚本的范式仍然是非常事件驱动的（只是不限于 JSON 事件所拥有的）。这是一个很大的概括，但我的看法是 JSON 中的定义和脚本中的逻辑大致分开。所以脚本将继续变得更强大，并希望与更多我们的系统集成。
-   **答**：哈哈，我没说取代，只是我认为重要的是我们要清楚脚本 vs JSON 的职责，以及它们如何很好地交互。你们应该很容易知道在 JSON 中做什么，以及什么时候跳到脚本中工作（反之亦然）🙂

## 客户端脚本

-   **问**：是否会有办法让我们制作客户端模组？或者如果这有意义的话， realms/世界上的脚本能够使用客户端？
-   **答**：客户端脚本是经常出现的事情，我们认识到它的价值。创建一个在客户端上运行的 JS 实例并不困难，但设计/创建/支持一个全新的客户端 API 是一项巨大的工作。对于 API 设计来说很困难（因为我们需要跨许多形式因素处理 UI 控件和输入方案），但对于创作脚本来说也是负担，因为它带来了两个不同脚本上下文的复杂性以及在它们之间明确同步的需要。
-   **问**：显然，许多客户端脚本模块正在开发中，但它们的路线图到底是什么？它们的意图和能力范围？请告诉我们关于它的一切！
-   **答**：在大多数情况下，我们专注于服务器端脚本 API，而且坦诚地说，在我们可以为大多数开发者保持简单的地方，我们希望将 API 添加到服务器端（例如，/server-ui 作为一个例子）。

我们知道有些场景需要客户端脚本——客户端验证、UI、输入管理可能——所以我们可能会跨越那座桥梁，拥有更正式的客户端脚本支持，但可能不是在短期或中期。那边有几个棘手的问题。而且再次强调，我们的偏见是尝试将尽可能多的东西放入服务器 API，只是为了保持简单。

-   **答**：我知道的另一个大想法也是最小化混淆。在我们考虑客户端脚本的场景中，它需要提供独特的价值，而不是简单地与服务器并行，因为它们本质上是不同的。我们希望绝大多数场景可以通过服务器处理（甚至编辑器在服务器上也有自己的输入管理！），但我们知道对客户端脚本的兴趣，以及可能最好由它服务的领域。

## 更好的脚本 -> 数据驱动交互

-   **问**：我们能否获得更多在脚本和资源包及行为包中的数据驱动文件之间发送信息的方式？
    能够为给定实体/可附着物从脚本向 molang 添加查询会很不错。例如，如果你们想在脚本中设置实体的骨骼角度，你们可以这样做：

```js
entity.setMolangFunction("wiki", "getMyAngle", () => {
    return 32;
});
```

然后在动画中，你们会写 `rotation: [0, "script.wiki:getMyAngle()", 0]`
这将允许诸如反向运动和从行为包运行动画，而不会浪费 q.skin_id 或 q.variant 或编辑 player.json。

-   **答**：实体属性是方法！让我们知道是否有任何场景实体属性不满足您的需求。
    从客户端到服务器的回调这个想法很有趣，但我们希望避免引入更多客户端权威行为。

## 你们是如何设计 API 的？

-   **问**：关于 API 结构做出了哪些决定，比如 API 有时如何使用方法而不是属性，你们为什么做出这些决定？
-   **答**：对于方法 vs 属性，我们内部有一个思考过程来决定。我会说我们不是 100% 一致的（这是一个不断发展的流程），但我们正在努力变得更加一致。
-   **问**：构建新的/重新设计现有脚本功能的 设计过程是什么？
-   **答**：我们创建 API 的第一步是思考它将被使用的情况。创作者希望使用此 API 实现什么游戏玩法？该系统的哪些部分很重要？创作者想要能够修改该系统的哪些部分，为什么？这有助于集思广益 API 的形状。如果 API 在 beta 中，我们会尝试重新考虑这些问题，以防在创建 beta API 时遗漏了重要的场景。

我们在这一阶段还要看的重要的事情是这将如何在我们的代码库中实现。有时我们会遇到某些限制，导致我们必须以不同于预期的方式设计 API。有时我们会遇到一个系统具有的更有趣的属性/能力，我们最终会将其添加到 API 中。

当我们同时考虑上述领域（场景和实现）时，我们根据创作者的需要和我们在引擎中能够实现的能力来塑造 API。然后我们提出一个规范文档，概述上述所有内容，以及 API 应该什么样的提案。然后我们作为一个团队审查它并一起迭代。一旦没有更多问题和关注点，我们就开始实现。

当然，实现过程中的发现有时会引发进一步的问题和担忧，导致我们进一步改变设计。

方法 vs 属性的要旨是"它简单（不复杂计算/设置）？把它设为属性，否则把它设为方法"

-   **问**：你们在制作 API 时追求什么品质？
-   **答**：确实有很多事情，但我认为可以提炼为几个要点：

1. 我们能否很好地保证这个 API 的向后兼容性？它有确定性行为和时序吗？
2. 它是否充分覆盖了预期的场景并与现有其他 API 良好交互？
3. 它易于使用，类型良好（以便快速获得智能提示），并且清晰？我们有大量测试，在内部我们编写 API 演示以确保它们易于使用。我也是让 TypeScript 类型帮助您更快编写代码的强烈倡导者。
4. 脚本 API 如何与或比较来自命令、JSON 或 molang 的现有功能？

一个非常大的目标是脚本是一个超稳定的平台来构建体验，但我们也知道脚本是游戏更广泛可扩展性表面的一部分。所以可用性 + 可靠性和兼容性的组合非常重要。

-   **问**：实现新 api 最不喜欢的部分是什么？在现有代码库中集成它困难/复杂吗？
-   **答**：作为非开发人员，我喜欢帮助设计 API 的整个过程。从决定哪些 API 对社区最重要或从 beta 中拉出，到进行设计讨论以决定如何使 API 恰到好处，再到将其发送给你们可爱的 folks 并获得反馈。那个过程最困难的部分可能是当实现开始时，我们发现我们代码库中的局限性限制了我们计划的 API 设计，导致我们改变设计计划。但我认为挑战是乐趣的一部分！🤪
-   **问**：你们如何决定如何为附加包中已存在的系统设计接口？
-   **答**：我们尽最大努力在命名方面保持 JSON 组件和脚本之间的对等，主要是为了创作者的熟悉。然而，有时我们认为 API 可以从命名和/或接口的分歧中受益，所以这不是一个硬性规则。

至于什么时候我们将 API 作为 getter vs 只读属性，我们尽最大努力保持一致，遵循一系列规则。例如，执行复杂计算的 API 通常是 getter，而只返回常量或预计算值的 API 是属性。话又说回来，这有点是一门艺术，而且我们在开发早期并不是非常一致，所以有一些例外。

## @minecraft/vanilla-data 模块

-   **问**：是否有计划内置此模块？手动包含它既不方便，也是初学者要经历的混乱环节。
-   **答**：不，没有计划将 vanilla-data 模块移入 server。事实上，我们最初想把它拉出 server 的一个大原因是：解耦 API 合约与数据合约。具体来说，我们将所有脚本 API 模块视为强 API 合约，当我们选择特定版本时，我们保证向后兼容性。这个合约真正定义了你们的可用行为和功能，而不是任何给定时间游戏中存在的内容类型。例如，您可以在 1.19.40 或 1.20.40 的基础游戏版本上使用 @minecraft/server 1.5.0，而"vanilla-data"（即可供您使用的方块或物品类型）在这两个版本之间会有所不同。我们的 API 合约对该合约没有任何保证，只有功能。所以当我们过去在 server 模块中有那个数据时，我们会因为不必要的原因经常更改 API，并在使用不同基础游戏版本的模块时添加问题。

但是！我们确实认为在了解任何给定基础游戏版本的可用原始版数据方面有很大价值，而且使用枚举调用 API 也更容易，所以将其分离出来并按游戏版本化非常有意义。

然而，它确实引入了一个小工具问题，因为现在它是需要包含在您的行为包中才能真正工作的 JS。一般来说，基线工具故事是我们经常思考的事情（绝对希望听到关于此的反馈！），并且我们也想让诸如轻松打包代码的事情为你们的工作流程变得非常容易。

另外，现在我已经将 vanilla data 设置为预打包在单个文件中，所以如果您不想做任何 TS 或打包工具，只需从包中获取 JS 并将其放入您的脚本文件夹，它应该可以工作。

但 TypeScript 很棒 😄
