## HCF 弃用/移除功能替代？

-   **问**：是否有计划带回 HCF 实验中弃用/移除的所有或部分功能，无论是直接重新引入还是通过新方法？作为示例的两个组件是物品的 `minecraft:knockback_resistance` 和方块的 `minecraft:unwalkable`。
-   **答**：当我们处理这个时，我们优先考虑了 HCF 中正在使用的部分，而那些没有被使用的，没有包含在初始工作中，然而这应该在我们 backlog 中跟进在将来（如果不在，这个问答后会是）感谢您的反馈！

## 为什么是最近的更改？

-   **问**：你们是如何想出非常有趣的最近更改的，什么促使了它？为什么用自定义组件替换 hcf 在你们看来是一个好主意？
-   **答**：HCF 事件存在一些稳定性、可扩展性问题，总体（我们感觉）使用起来很笨拙。最终，我们决定我们需要为一个长期支持该功能的完全不同的解决方案。脚本更加稳定，更容易扩展更多功能，与其他现有功能更加一致，同时也更强大。我们迭代了几种集成脚本和 JSON 方法，最终导致了今天自定义组件的状态。我们确实有一些改进计划在明年某个时候与您分享！总体而言，我们认为自定义组件为创作者提供了更多力量，并且比 HCF 事件从 Bedrock 平台获得了更好的长期支持。

## 自定义方块实体

-   **问**：是否会有机会创建自己的方块 - 箱子？
-   **答**：这不在我们近期的路线图上，但我们正在积极研究所有无法在数据中复制的方块行为！
-   **问**：是否有计划添加方块实体？或者，至少，方块动画？
-   **答**：绝对是一个值得探索的领域。我认为使用自定义方块组件（脚本）让它更容易"伪造"这个。我认为方块实体的大部分功能都可以用它来模拟。一个你不容易做的是方块特定的存储（如箱子库存），所以如果能以某种方式启用会很好。

## 自定义组件

-   **问**：是否有计划允许数据绑定到自定义组件，而不是我们目前拥有的 has 或 does not have 接口？
-   **答**：这是一个我们期待做的功能，并将在明年某个时候推出。我们希望将自定义组件扁平化，使它们看起来和感觉更像其他组件。
-   **问**：这包括参数吗？它们会更快来吗？参数会使自定义组件在物品和方块之间以及项目之间更容易共享。
-   **答**：自定义组件扁平化和参数可能会一起发布，而且可能还需要脚本版本 2.0.0。目前我们说这两个功能都将在明年某个时候推出

## 更多与 ScriptAPI 合作：

-   **问**：我不知道其他人在创建附加包之前在做什么，但我是来自 JavaScript 网站创建/Discord 机器人创建背景，我发现很难很好地处理所有那些 JSON 文件我不是建议完全废除它们，但我希望将方块和物品的视觉特征留在 JSON 文件中，并将涉及事件、函数等的所有其他内容移至 API，这是大多数任何开发的主要部分，使用主要部分在编码语言如 JavaScript 或对于 Minecraft Java 好吧。说出那个可能会让一些人生气（HCF 移除也有仇恨）但是的作为一个 general 开发人员发现它在开始附加包创建时很奇怪和混乱

在我脑海中它会是这样的

-   您的 JSON 文件（获取关于您的方块/物品 的基本信息，如纹理、几何体、类别等）
-   将该 JSON 文件导入您的脚本
-   注册方块/物品
-   并使用 API 功能。（我不知道例如 item.attackDamage(Int) 等，或者generally 与视觉方面无关的所有东西，所以大部分是方块/物品的行为）

-   **答**：我认为总的来说我们一直在缓慢地向"JSON 是定义，脚本是逻辑"方向发展，我认为这是你帖子的想法（虽然有更多"魔法 hookup"，不需要将 JSON 导入脚本）。

## PlayerInteractWithBlock

-   **问**：我最近一个月左右没有参与附加包，但是，我记得（至少当时）我们不能与稳定中的原版方块交互 - 您必须使用 itemUseOn，因为它需要一个手持物品，因为 PlayerInteractWithBlock 仍然在 beta 尽管在文档中列为稳定。这改变了吗？如果没有，我们是否应该期待在未来稳定中看到它？
-   **答**：我们知道这个在 beta 中待的时间比我们预期的长 😕 但我们希望 PlayerInteractWithBlock 应该在即将到来的版本中进入稳定。我们感受到了。
-   **问**：愿意分享你们一路上发现什么问题吗？
-   **答**：对于玩家交互事件，我们与之搏斗的问题是它们以难以预测甚至依赖于设备的方式频繁重复……这使其成为不可预测的 API。

    我们考虑对该区域进行更大的重构，但我认为鉴于所有行为和设备都捆绑在其中，这是"冒险的"。我们最终做的是添加额外数据（一个 isFirst 属性），可以帮助创作者知道它是否是事件系列中的第一个交互。创作者可能仍然需要某种内部跟踪器来知道"这是不是我看到的第一个事件"这并不太棒。
