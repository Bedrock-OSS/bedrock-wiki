本次问答在 [Bedrock Add-Ons Discord](https://discord.gg/NGeNhZpvzV) 举行。五位 Microsoft 员工加入我们，回答了关于 Gametest 框架的问题。问题来自社区征集。

_警告_：并非所有消息都被完整记录，部分内容经过编辑。如需查看完整内容，请加入上述 Discord 并获取"events archive"角色。

## Realms

-   **问**：GameTest 是否设计用于在 Realms 上工作？

-   **答**：是的

## QuickJS 与 V8

-   **问**：选择 QuickJS 而不是其他 JS 选择（如 V8）的原因是什么？QuickJS 慢得多（主要是因为它缺乏 JIT），在某些社区中这是使用它的一个大缺点

-   **答**：我们中一些人在过去项目中使用过 QuickJS，它非常容易集成。我们研究过 V8（和其他），将来可能会转向它们。JIT 非常可取，但并非所有平台都支持（容易，或根本不支持）。

## 文件与网络访问

-   **问**：gametest 是否会有文件或网络接口？

-   **答**：我们希望默认保持脚本 API 更有限，并随着时间添加功能。文件和网络 API 需要特权，可能需要游戏所有者同意，因此这些可能不会成为默认 API 集合的一部分，但我们可能会在以后添加这些功能（例如，可能用于服务器所有者）

-   **问**：这样的接口只会实现在所有可用平台的一部分上吗？

-   **答：**我们努力在所有平台上实现所有 API。唯一的例外是如果我们引入一些可能是桌面专用的编辑器特定 API。

## 斜杠命令

-   **问：**我们什么时候能够注册自定义斜杠命令？

-   **答：**虽然我们没有具体的时间表，但这在我们构建列表中很高。

-   **答：**当人们开始制作自己的 !命令时，很明显我们需要这个。

## 测试原版

-   **问：**你们目前是否使用 GameTests 框架来测试原版行为包？或者，您以何种方式使用测试 API 来测试您自己的内容？

-   **答：**是的！我们现在有很多原版内容的测试，并希望随着时间的推移扩展到更多。实际上，我们将在公共构建中运送一些我们为原版内容拥有的测试（vanilla_gametest）。

-   **答：**理想情况下，随着时间的推移，社区也会帮助我们使用 GameTest 报告原版的 bug，我们可以合并这些测试（一旦我们修复问题）并确保我们不会再破坏这些东西 🙂

## 时间线

-   **问：**我们能否获得 API 下一个计划添加的事件的时间表？

-   **答：**我们的团队仍在决定下一个添加哪些事件，所以没有太多时间表可以分享。您希望看到添加哪些事件？

-   **答：**绝对同意方块破坏/放置是高度优先的

## GameTests 的政治

-   **问**：什么技术、结构或政治原因允许 GameTests API 蓬勃发展，而原始 Scripting API 没有？你们能谈谈这次有什么不同吗？此外，如何认为 GameTest 是"成功的"（因此不会放弃）。有什么我们可以帮助的吗？

-   **答**：一般来说，我们正试图非常专注于我们针对的场景，从内容测试和验证开始，我们可以为不仅仅是核心 Minecraft 还有 Minecraft 中的自定义内容使用更多。我们真的希望为人们围绕他们的内容构建和构建测试更简单。那个场景也有更有限的要求（例如，我们可以在更少的平台上，perf 不太是问题，等等）。所以，我们专注于 GameTest，而为了让 GameTest 成功，我们希望看到它对内容创作者测试他们的东西很容易。

-   **答**：当然，我们确实看到更多场景的未来——包括游戏玩法——但我们真的不想让任何人期望过高（或让人对脚本/gametest API 下注用于游戏玩法），直到我们对 perf 等有更多验证，并获得更多平台支持，并响应您的反馈。

-   **答**：RE: 有什么我们可以帮助的吗？- 继续与我们互动以改进和添加新东西！🙂 创作者社区是所有这些的驱动力。

## 游戏机

-   **问**：游戏机不能运行 gametests 的原因是什么？游戏机是否会在未来支持 gametest API？

-   **答**：是的！我们计划支持我们所有的平台，几个平台没有我们的 JS 引擎所需的所有 API，aligned_alloc 是其中之一。我们正在积极努力启用这些平台。

## 其他语言

-   **问**：是否有任何支持 gametests 支持不同语言的计划？

-   **答**：我们实现绑定层的方式足够通用，可以适应其他编程/脚本语言。在内部我们做了一些有趣的事情，比如摆弄 Lua 甚至像 Blockly 这样的东西。但我认为目前我们无法承诺为任何其他语言添加官方支持 🙂

-   **问**：你们考虑过 Kotlin 吗

-   **答**：我没有深入研究 Kotlin（我们所有 Android 平台仍然用 Java 编写 🙂）但那听起来很酷！ 我会找时间看看。

## 事件系统

-   **问**：既然数据驱动中也有事件系统。你们如何定位 gametest 框架中的事件系统与数据驱动中的事件系统之间的关系？将来会提供两者之间的接口吗？

-   **答**：我们希望系统能够很好地协同工作。如果您熟悉数据驱动构建，我们希望您能够以有意义的方式加入脚本。我们仍在研究这到底会是什么样子。

## 我们的"不实现"清单有哪些内容？

-   **问**：能否分享一下你们明确"不会实现"的功能清单？比如某些不支持的平台，或者不打算采用的 API 设计方向。基本上就是任何非桌面端的内容。

-   **答**：好问题。我们明确"绝对不会做"的清单其实很短。

-   **答**：以下是我们"极其谨慎对待"的清单：

    -   网络访问
    -   文件访问
    -   平台专属 API

-   **答**：网络访问方面，我们可能会通过高度结构化的 API 来允许访问特定目标。文件访问也是类似思路：可能会提供某种形式的持久化存储，但不会开放自由的文件系统访问。

-   **答**：平台专属 API 是我们希望尽量避免的。不过可以设想为编辑器场景实现一些桌面端专属 API，但在游戏玩法和 GameTest 场景中我们会避开这种做法。

-   **答**：还有一个我特别想支持但实现起来极其困难的功能是自定义着色器。PlayStation 要求着色器必须内置于提交包中，所以我们可能只能通过提供基于物理的渲染材质系统来解决，在这个系统中对高度灵活的着色器进行硬编码。

-   **问**：关于刚才提到的"持久化存储"，我们能否以跨存档的方式读写简单的整型变量？还是说数据仍然绑定在特定存档实例中，游戏结束时就会被清除？

-   **答**：是的，我们计划添加键值对存储，可能是 JSON 格式的存储。一种是用于访问标签和记分板的 JavaScript API。更进一步的话，会支持通用的读写存储（但依然不是直接的文件系统访问）。我们需要解决一些安全问题，确保存储空间按行为包进行沙盒隔离。

## 自定义维度

-   **问**：如果真的发生，GameTest 会支持自定义维度吗？

-   **答**：在设计 GameTest API 时，我们一直在考虑自定义内容。例如，这就是为什么 Commands.run 接受维度作为字符串，而不是硬编码的维度变量。所以我们肯定为将来与自定义维度和其他自定义内容的集成留下了可能性。

## 旧脚本 API

-   **问**：旧的脚本 API 会怎样？它仍然可用但不再更新吗？（即它永远不会被弃用）

-   **答**：原始脚本 API 将可用（正如您注意到的，它在最近确实没有得到太多更新。）随着 gametest API 和其他游戏玩法逻辑系统的发展，可能会覆盖脚本 v1 的能力，我们将删除脚本 V1 功能。

-   **答**：旧脚本 API 是实验性的，所以几乎没有（嗯，任何）向后兼容性保证。旧脚本 API 在移动设备上不可用，我们此时不会扩展其平台支持。

-   **答**：我们确实希望支持客户端体验和 UI 之类的东西——我们有一些如何做的想法，但还没有 firm 计划

## 世界生成

-   **问**：有任何计划在 GameTests 中公开世界噪声吗？JS 存在噪声库，但需要的是生物群系生成中使用的噪声/Molang 查询。

-   **答**：我们还没有仔细研究我们希望如何允许世界生成存在于脚本中。区块生成在任务线程上运行，目前我们的 gametest 实现不允许安全迁移到其他线程。
    我们有一些想法来创建类似于 web worker 的东西，但目前只有对话。

## GameTests BDS

-   **问**：gametest 会在 BDS 上顺利运行吗？

-   **答**：我们目前在我们 CI 管道中使用 BDS 来运行 GameTest 并验证结果！

-   **答**：BDS 和 GameTest 有哪些地方相处不好？

-   **答**：GameTest 可能无法工作的一个原因是世界需要启用实验，这在专用服务器上不容易做到。最简单的方法是使用 Minecraft 客户端生成世界并打开 GameTest 实验，然后将世界转移到专用服务器。

## GameTests 的终极目标

-   **问**：GameTests 的确切终极目标是什么？它会保持作为测试工具，还是会扩展，也许添加全新的内容？

-   **答**：对于 GameTest，我们正在寻找使内容测试和验证变得更加容易。我们希望人们围绕他们的内容、他们的装置和他们的脚本构建测试变得简单。部分原因是用于模拟和测试断言的丰富脚本 API，我们已经用 GameTest 模块构建了。我们还将向 GameTest 添加一些新 API，包括一些非常酷的方法来在环境中模拟玩家。我们还在努力找出使其更容易创建这些基于 JavaScript 的测试的方法。

-   **答**：当然，GameTest 的一个快乐的副产品是有机会构建更多通用基于服务器的脚本 API，这帮助我们探索它如何在未来的场景中使用。

## GameTest 是通用的吗？

-   **问**：看到社区对 gametests 的利用主要是将它们作为最终产品的一部分（就像脚本引擎设计的那样），而不是严格用于生产中捕获 bug，您是否看到 gametests 被重新用于更多通用应用并成长为被认为是附加包的受支持功能？

-   **答**：我们目前专注于内容测试的 GameTest。在支持通用游戏玩法目的的脚本 API 之前，我们希望确保我们做更多测试并添加更多幕后基础设施，以确定这些脚本 API 何时以及如何脱离实验，以便它们可以在那些角色中使用。

-   **答**：肯定是两者的混合！我们一直在添加一些新的 GameTest API 来测试一些原版行为，但我们也想知道你们对哪些 API 感兴趣。

-   **答**：这很好的例子是自定义命令 API。这是我们清单上的高优先级，因为社区一直在询问它 :smile:

-   **答**：只是另外几个功能将使 gametests 更强大和更容易创建：模拟玩家 API，以及 Visual Studio Code 中的脚本调试

## 平台的效率

-   **问**：与其他平台/总体效率的兼容性如何？

-   **答**：我们预计将在所有平台上启用它。关于性能，我们确实必须跨越支持即时编译和不适用的平台。所以那是我们大量已知的分析和性能调整的领域。

-   **问**：通过一般效率，我的意思是 API 离底层有多"近"

-   **答**：谢谢您澄清效率：我们的 API 将尝试从一开始就"与数据驱动系统很好地合作"。因此在 Minecraft 实体、物品、方块、区块等抽象级别运营。如果您在熟悉 Bukkit，我们试图让它与那个相似的抽象级别（加上客户端侧添加也在我们的野心范围内）。

## 为什么是这个名字？

-   **问**：GameTest 这个名字的原因是什么？

-   **答**：我们在 Java 做过的工作的基础上构建。他们构建了一个初始 GameTest 框架，他们用于测试过程。

-   **答**：对此的跟进，的计划是将整个系统称为 gametests 还是别的什么？

-   **答**：我认为如果我们超越测试场景，将整个 JS API 集称为 GameTest 并没有意义。您可以在整体 API 命名中看到一些这种思路。

## 为什么选用 GameTest？
 
-   **问**：您和您在提出它的用途时的想法是什么

-   **答**：基本上：测试游戏！允许测试添加到游戏中而无需重新编译是一个很棒的工具。我们可以更快地处理测试，社区成员可以在报告 bug 时编写测试。

-   **答**：GameTest 也是我们在让脚本在 Minecraft 中运行方面的伟大"试验场"。

## GameTest 的限制是什么？

-   **问**：gametest 的限制是什么？
-   **答**：只有您的想象力！

-   **答**：不过，我们有一些限制：结构限制为 64x64x64。我们目前只在主世界维度运行，但我们希望拓宽这一点。

-   **答**：我们目前不支持与玩家交互，但那正在深度开发中。

-   **答**：GameTest 在移动设备上工作。我们正在努力支持唯二暂时不支持的平台：Switch 和 PlayStation。

-   **问**：在崩溃游戏之前我可以嵌套多少个 for 循环？

-   **答**：实际上，这是一个好问题。现在如果您 while (true) 您将挂起游戏。但我们原型并计划构建一个"watchdog"，能够检测并停止这种情况。

-   **答**：我们的 watchdog 原型做的更多。它还能够监控脚本对象计数和内存以及循环。
    （并且跨语言运行时工作，所以这很酷）

-   **答**：作为一个编写了一堆 gametest JS 的人，肯定在我们的脑海里和路线图上有一种更容易的方法来重新加载 JS

## Hummingbird UI

-   **问**：gametest 会继承脚本作为 Hummingbird UI 的引擎吗？

-   **答**：Hummingbird 是 GameFace（https://coherent-labs.com/products/coherent-gameface/）的曾用名。这是一种我们正在使用的 UI 技术来构建新的 Bedrock UI。

-   **答**：我们当然计划允许脚本创建或修改 UI。但是，我们希望它与内置 UI 以自然的方式工作，我们仍在研究它将如何工作。

-   **答**：我们不希望与 GameFace JS 在同一个沙盒中运行。而且，现在我们专注于服务器优先，而 GameFace 只在客户端运行。

## 外部脚本

-   **问**：gametest 会与外部脚本一起工作吗？这样他们可以与在不同目录中运行的脚本通信

-   **答**：我们确实希望为脚本提供一种方式来依赖其他脚本的方式——例如，一个非常好的用于测试的脚本，或者用于地形 gen 的脚本——但那可能通过行为包依赖系统。我不认为我们有一种从任意位置加载 JS 的方法。

-   **答**：是的，让外部脚本在所有平台上工作会很困难。而且可能也是安全挑战。

## 市场

-   **问**：GameTest 是否可用于市场内容？如果是，大约什么时候？

## Java 对等

-   **问**：许多标记为 suite:java_parity 的原版游戏测试被禁用，可能是因为行为不能正确工作。这些测试是从 Java 的测试套件移植的吗？这些测试的意图是什么？

-   **答**：我们正在根据 Java 内部的一些 GameTest 工作来构建这个，其中一些测试也被移植了。我们也想带来并跟踪 Java 所拥有的一些测试，即使 Java 和 Bedrock 之间存在差异可能导致它们无法以相同的方式工作

-   **问**：很高兴看到禁用的对等测试作为移植更多 java 行为的待办事项，我们绝对可以提供更多，ahaha...

-   **答**：如果您编写一个证明 Java 对等问题的 GameTest，我们很乐意接受它：https://aka.ms/gametestsamples

-   **答**：是的，我们正在跟踪通过 GameTest 发现的对等问题和 bug。

-   **问**：如果 GameTest 以这种方式开放贡献，我们是否能够为实际原版行为/资源包做出贡献？

-   **答**：我们目前正在讨论是否应该将"内置" GameTest 移到同一存储库中，并使其更容易获得开源行为包包
