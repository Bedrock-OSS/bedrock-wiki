::: warning
本页主要使用来自多个来源的社区反馈编译。因此，一些信息可能是笼统的、主观的或冲突的。优化附加包时始终使用您自己的最佳判断。本页不能替代在各种设备上测试您的附加包。

附加包中的性能至关重要，因为即使是最技术性的附加包，如果大多数玩家无法体验它，它也基本上没用。在开发附加包时，应该始终考虑到许多 Bedrock 玩家将在比您开发所用设备明显更低的设备上体验它。这对移动用户尤其真实。因此，应该在开发附加包时考虑性能，并在可能的情况下在低端设备上测试性能。

本指南是 Bedrock 版各个子系统的特定性能注意事项的非详尽列表。不应将任何单点作为硬性规则。相反，这些性能注意事项应帮助您识别潜在的改进区域。

## 生物群系和功能

### 生物群系

-   生物群系系统通常非常高效
-   高度图的大值通常可以优雅处理
-   `climate` 组件会产生大粒子风暴

### 功能

-   生物群系通常比功能生成造成更少的延迟。
-   已经以低性能成本实现了每个区块数百次迭代的多方块功能。
-   每个区块数千次迭代的多方块功能会对游戏玩法产生负面影响。
-   已经以低性能成本实现了每个区块数十万次迭代的单方块功能。
-   每区块数千个功能实例几乎没有成本。
-   每区块数万功能实例对区块加载有显着影响。
-   每区块数十万功能实例会将区块加载减慢到无法忍受的程度。

## 方块

### 材料

-   应该始终使用渲染所需的最小材料类型
    > `alpha_blend` 性能比 `alpha_test` 差，`alpha_test` 比 `opaque` 差

### 数量和类型

-   应避免和最小化流动的液体

### 更新

-   应该最小化方块更新

## 命令

### 数量和类型

-   最小化每 tick 运行的命令数
    > 每 tick 运行 `/effect` 和 `/gamemode` 是可以避免的，并且具有显着的性能影响
-   运行时应避免大型 clone、fill 和结构加载
    > 将这些更广泛的操作分解为分布在多个 tick 上的多个命令将避免延迟峰值，考虑使用结构加载动画

### 选择器

-   应注意确保函数不会在太多实体上执行，因此也不会执行太多次
-   执行记分板命令的成本超过多次解析同一实体选择器的成本
-   使用 c=1 确保选择器找到一个实体时停止可以提高性能
-   当使用相同选择器执行多个命令时，使用函数以避免重复解析同一选择器

### 标签 vs 记分板

-   记分板在大规模上表现更好

## 实体

-   实体通常具有按子系统划分的最大性能影响之一，因此应在可能的地方最小化

### 组件

-   飞行生物的寻路有显着的性能成本
-   飞行生物通常会遇到性能问题
    > 如果可能，应该考虑通过动画伪装飞行生物

### 假人实体

-   假人实体通常与真实实体具有相同的性能影响，除了排除寻路等重组件

### 几何体

#### 骨骼

-   观察到的骨骼数量没有性能影响

#### 元素

-   元素数量通常不是问题，除非在达到数千个元素的极端情况下

### 材料

-   应始终使用实现所需效果所需的最小材料
-   如有疑问，参考材料定义文件以了解各种材料的成本，同时考虑材料继承系统

### 数量

-   任何给定时间加载的实体应最小化
    > 低于 30 是最佳的

## 光照

### 地图注意事项

-   中空区域会导致光照计算延迟，即使您看不到它们
    > 通过填充未使用的封闭区域避免这种情况
-   保持地图设置为白天或夜间将避免光照重新计算

### 光源

-   Bedrock 光照是动态计算的，这意味着不同的光源有不同的性能成本
    > Light blocks 性能最好，因为它们缺乏粒子、渲染和特定状态逻辑

> 火把是次要的性能问题，因为它们发射粒子、渲染，并具有依赖于它们连接的方块的特定状态逻辑

> 具有最小组件的自定义 light blocks 是性能和美学之间的合理折中

## Molang

### 递归

-   尽可能减少递归的使用
-   密集的嵌套循环结构将导致性能问题
-   尽可能使用 break 跳出循环

### 结构

-   避免使结构太深，因为每一层都有性能成本

### 变量

-   尽可能使用临时变量以最小化内存中加载的变量
-   考虑变量多长时间计算一次基于脚本类型

## 纹理

### 纹理列表

-   大量纹理会严重影响游戏性能。创建 [`textures_list.json`](/concepts/textures-list) 文件。

### 数量

-   不应使用超过 3000 个纹理。
这是因为 Render Dragon 施加的限制

> Render Dragon 有 4096 纹理数量限制，截至 1.16 有 800 个原版纹理

### 分辨率

-   最大纹理分辨率是 16384×16384
-   建议的最大纹理分辨率是 4096×4096 以保持与低端设备的兼容性
-   请记住，方块和物品纹理是[合并的](/concepts/texture-atlases)，更大的纹理可能会在低端设备上破坏图集生成
-   仅在需要时制作纹理以传达在所需距离所需的细节

## 交易

村民交易会造成性能问题并在所有设备上甚至在 60 次交易或更多时崩溃。避免为一个实体进行大量交易。解决此问题的最佳方法是将您的交易分成两半并将它们转移到另一个村民或自定义实体/npc，30 次交易是测试中的一个很好的安全数字。_可能是 JSON UI 问题_

## 声音

### 数量

-   报告称注册的声音总数对性能有影响

### 压缩

-   声音压缩对包大小非常有益
-   这在旧的和低功耗设备上尤为明显，如 Switch
-   Bedrock 使用的 FMod simple API 在加载到 RAM 之前将所有声音解压为 WAV，意味着在这方面没有 CPU 性能改进
    -   如果音频是流式的，则不会发生这种情况

### 流式传输

-   一般来说，大小超过 500kB 或长度超过 1 分钟的声音应该流式传输

## 红石

### 区块边界

-   应避免使用红石跨越区块边界

### 命令方块

-   创建大型命令链时，垂直堆叠并在单个区块中
-   尽可能在功能和行为中最小化命令方块的使用

## 区块加载区域

-   总区块数比区块加载区域更重要
-   除非必要否则应避免动态区域
-   最佳做法是将区块加载区域最小化到一个区块（如果可能）
    -   所有始终开启的红石应该适合这个区块加载区块
-   当不再需要它们时卸载区块加载区域，通过 /testforblock 测试

## 文件

-   大量文件会严重影响游戏性能。创建 [`contents.json`](/concepts/contents) 文件。
